THE DEFECT (source-confirmed): `replace_inner` (main.rs:2404-2409) is a wholesale swap — `*inner = next; changed = old.surface_mode != next.surface_mode || old.tools != next.tools`. `next` is built purely from desired policy (desired_session_from_catalog → session_inner_from_desired → refresh path at 3040-3097). So when a policy refresh REMOVES a tool that was `ToolBinding::AckOnly` (e.g. ctx_reduce flips tool_present true→false), the binding vanishes from BOTH `inner.tools` (the advertised list) AND `inner.bindings` (the dispatch table) in the same instant. An MCP client with a STALE advertised tool list (its tools/list_changed re-list hasn't completed) can then call the tool and hit the unknown-tool path — surfaced to the model as an error. Note the contrast: the ROUTE-death path already retains AckOnly bindings (the retain at main.rs:2391-2396, "Ack-only bindings survive route death"); it is specifically the POLICY-REMOVAL swap that lacks retention.

THE LOCKED FIX (generic hidden tombstone — zero ctx_reduce-specific knowledge): in `replace_inner`, after computing `changed` but conceptually as part of constructing the new state: for every entry in the OLD `inner.bindings` that is `ToolBinding::AckOnly` AND whose name is ABSENT from `next.bindings`, carry the OLD AckOnly binding (the SAME value — same `acks` Arc counter, cloned Arc not a fresh counter) into `next.bindings`. Do NOT add anything to `next.tools`. NEVER retain a `ToolBinding::Forward` this way (a removed Forward tool must fully vanish — it owns route state). Resulting semantics:
- The tool disappears from the advertised catalog / tools list IMMEDIATELY (coherent with the policy).
- A stale-advertised call still resolves in the dispatch table to the inert ack ("Queued for context compaction." — the existing ack_only_tool_result / ACK text constant; do not restate the string, use the existing constant/helper) instead of unknown-tool.
- The tombstone structurally cannot own a route: ToolBinding::AckOnly carries no route by the sum type.
- Lifetime: the SessionInner's = the MCP session. Re-adding the tool via policy replaces the tombstone with the new desired binding naturally (next.bindings already contains the fresh entry, so the carry-over condition "absent from next.bindings" is false).
- The `changed` computation must still fire correctly: the tombstone carry-over must NOT make `changed` false when the advertised tools DID change (changed compares tools, not bindings — verify this stays true), and must not itself flip `changed` when nothing else changed on a refresh that re-evaluates identical policy (tombstones carried again idempotently).

IMPORTANT IMPLEMENTATION DETAIL — idempotence across repeated refreshes: on a SECOND refresh (policy still lacking the tool), the tombstone now lives in the CURRENT inner.bindings as an AckOnly absent from the new next.bindings → the same carry-over rule re-carries it (same Arc). That is the desired fixed-point: repeated refreshes neither drop, duplicate, nor reset the tombstone/counter.
