# @cortexkit/private-files

Version 0.1.0; release tag prefix **`private-files@`** (for example, `private-files@0.1.0`). This standalone package lives in [`clients/private-files`](https://github.com/cortexkit/subconscious/tree/master/clients/private-files) in the subconscious repository.

## API

```ts
import { createOwnerOnly, verifyOwnerOnly, readOwnerOnly, EXTRA_ACE } from '@cortexkit/private-files'
await createOwnerOnly(absolutePath, { kind: 'file' }) // exclusive, empty creation
const result = await verifyOwnerOnly(absolutePath)
if (!result.ok && result.refusal.reason === EXTRA_ACE) {
  console.error(result.refusal.sid, result.refusal.mask)
}
const bytes = await readOwnerOnly(absolutePath) // verify and read the same opened handle
```

`createOwnerOnly(path, {kind: 'dir'})` creates one directory, not a recursive tree. Creation does not repair an existing object. `createPrivateFile(path, bytes)` combines secure exclusive creation, same-handle verification, and writing; `createPrivateDirectory`, `verifyPrivatePath(path, kind)`, and `securePrivatePath(path, kind)` are also available. `securePrivatePath` explicitly replaces permissions on an existing object owned by the process user; it does not take foreign ownership. Windows permission replacement changes only the pinned object, without propagating ACL changes to existing children; new children can still inherit its directory ACE. Secure existing children explicitly if needed. Tightening permissions cannot undo prior exposure or invalidate already-open foreign handles; rotate credentials when the consumer's migration policy requires it. Native errors include a path, `win32Code`, and `reason`, never secret bytes.

`verifyOwnerOnly` returns `{ok: true}` or `{ok: false, refusal: ...}`. Exported string constants are `WRONG_OWNER`, `EXTRA_ACE`, `NOT_PROTECTED`, `NULL_DACL`, `EMPTY_DACL`, `REPARSE_POINT`, `UNSUPPORTED_FILESYSTEM`, and `MODE_REFUSAL`. Wrong-owner includes `ownerSid` (on POSIX, `uid:<numeric owner uid>`); extra-ACE includes `sid` and `mask`. Additional diagnostic refusals are `unsafe-ancestor`, `wrong-kind`, and `io-error`. Filesystem absence/errors are not reported as successful verification.

## Policy and boundaries

Windows creates objects with owner explicitly set to the **process token user SID**, a protected DACL, and exactly one explicit ACCESS_ALLOWED ACE granting that SID FILE_ALL_ACCESS (`0x1f01ff`). Directory ACE flags are OI|CI (`3`); file flags are `0`. No SYSTEM or Administrators ACE is added. Reads accept only the token user, **BUILTIN\\Administrators (S-1-5-32-544)**, or **LocalSystem (S-1-5-18)** as owner. Other default owners, including non-privileged groups, are refused because owners have implicit WRITE_DAC. An elevated Rust writer can use Administrators as its default owner: that file remains readable from any process of the same user, elevated or not, because the owner is accepted by SID regardless of the reader's own TokenOwner. The DACL must still grant only that user's SID; an accepted owner does not grant another user's process read access. Permission replacement continues to require the token user as owner. Reads also accept one inherited file ACE (`16`) with an unprotected DACL **only when the immediate pinned parent has the canonical protected directory template**. Directories must always be canonical. Null, empty, foreign, denied, conditional, object-specific, and unknown ACEs refuse.

Directories are created and opened atomically by NtCreateFile with the protected descriptor. Verification and failed-create deletion use only that returned handle. New file leaves deny all sharing until writing and FlushFileBuffers finish, preventing concurrent readers from seeing partial secrets; ancestor share modes are unchanged. Native write copies and read buffers are zeroized before freeing, including on errors (returned JavaScript buffers remain the caller's responsibility). All blocking Win32 calls run in N-API async work. Transactions pin all ancestors without delete sharing, inspect every component for reparse points, and refuse ancestry where ordinary other principals can delete/replace the traversed component or rewrite its owner/DACL. Creation additionally refuses parents where those principals can pre-create the new name. SYSTEM, Administrators, and TrustedInstaller control of OS ancestors is outside this discretionary threat boundary; they are not allowed ACEs on private objects. No ACL verification is cached. Impersonation is unsupported. Metadata-only ACL checks determine why a path fails the owner-only policy without requesting file-data rights; if a Win32 open is access-denied, an exact-rights `NtCreateFile` security handle requests only owner-implicit READ_CONTROL. Repair uses READ_CONTROL|WRITE_DAC on that exact-rights path. Neither the metadata-only nor permission-repair `NtCreateFile` open requests synchronous native IO options, and metadata-only handles never consume bytes. When a data open fails, the backend may open a separate metadata-only handle and use its descriptor to report a typed ACL refusal. The metadata handle is then closed without reading file bytes, and a failed data open never becomes a successful read.

Only absolute, unambiguous local drive paths on fixed ACL-persisting volumes are supported. UNC/network paths, FAT/exFAT, reparse points, dot/trailing-space components, streams, and reserved DOS device names (including extensions and ancestor components) refuse with remediation. Reads are bounded to 64 MiB. Administrators exercising privileges, the same user's other processes, backups and offline access are outside the policy. This primitive is not an atomic replacement/lease implementation; publication, retries and credential migration remain the consumer's responsibility.

On POSIX, the package uses ordinary `0600`/`0700` creation and chmod, with normal umask behavior. It does not load native code or require a compiler. Verification uses lstat without following leaf symlinks and requires the current process uid as owner as well as exact `0600`/`0700` modes. Reads open with O_NOFOLLOW and inspect the opened handle's kind, mode and uid before consuming bytes; symlink leaves and foreign-owned private-mode objects refuse. These POSIX checks do not pin or prohibit symlinks in ancestor components.

## Building, distribution, and real proof

Install dev dependencies with `bun install --frozen-lockfile`, then run `bun run typecheck`, `bun run build`, and `bun run test` in this folder. The POSIX tests run on macOS and Linux without a native compiler. On Windows run `./native/build.ps1` with MSVC and the Windows SDK installed. It downloads checksum-verified Node headers/import library, compiles C with N-API v8, `/DELAYLOAD:node.exe` and a host-executable delay hook that resolves N-API symbols from the running Node or Bun executable, and emits `prebuilds/private-files-win32-{x64,arm64}.node`. The loader selects **process.arch**, so x64 Node emulated on ARM64 Windows uses the x64 binary. There is no install-time compilation and no mode fallback when a binary is missing.

`/DELAYLOAD:node.exe` and the host-executable hook are both required for Bun: normal node.exe imports would bind the addon to a separate Node image instead of the running Bun executable. The same binary per architecture works in qualified Node and Bun hosts. Hosts that do not export the required N-API symbols from their main executable are unsupported. In those hosts delay-load symbol resolution fails (potentially as a native loader exception or process termination, before the wrapper can report a JavaScript error). There is no LoadLibrary fallback or search for another Node image.

The `private-files-prebuilds` CI matrix produces both architectures as artifacts, never checked-in binaries. A distributor assembles both artifacts under `prebuilds/` before packaging; `prepublishOnly` checks their PE architecture and requires node.exe imports to be delayed, not bound to a separate Node image when Bun loads the addon. CI records `dumpbin /imports` and first runs each Bun's one-line addon load in a separate step, so a loader crash is distinguishable from a test failure. No release or publication is performed by the qualification workflow.

The Windows qualification matrix uses Server `windows-latest`, older Server `windows-2022`, and `windows-11-arm`, with Node 24 and Bun 1.3.14/1.4.2. Bun added native Windows ARM64 support in 1.3.10: [setup-bun's change](https://github.com/oven-sh/setup-bun/commit/0ff83bfc51e05dd2251088164ec6a5e8533b476b) and [1.3.14 release notes](https://bun.sh/blog/bun-v1.3.14). The loader rejects native ARM64 Bun versions older than 1.3.10 or whose version string cannot be parsed, rather than attempting to load an unqualified addon. The ARM runner also loads the x64 binary using emulated x64 Node.

Run `./test/windows/run-acl.ps1 -Runtime node` or `./test/windows/run-acl.ps1 -Runtime bun -ExpectedVersion '1.4.2'` **from this folder**, after building TypeScript, the native addon and the Rust fixture. The harness uses independent PowerShell/.NET descriptors, a standard-user probe with a public read control, a standard-user native writer/reader, forbidden ACL/reparse fixtures, migration/rename checks, and disabled-verifier mutation evidence. Descriptor/OS/filesystem/runtime/timing records are written outside build directories to `private-files-evidence/`. Fixtures that cannot be exercised fail rather than skip. The suite gives every test an explicit 120-second timeout under both Node and Bun, covering standard-user profile provisioning rather than relying on Bun's 5-second default. Bun steps also require the exact expected runtime version, so failed setup cannot qualify the previous installation. The wrapper runs Bun through `bun test` and requires exactly 21 passes with no skips/failures for either runtime; the count guard is itself tested by skipping all real assertions and requiring refusal. The Rust fixture pins **crates.io subc-os 0.1.14 and cortexkit-lease 0.1.3**, with its own Cargo.lock, and exercises both protected and inherited Rust-written files. Any rejected Rust ACL is reported verbatim; the reader is not weakened to match it.

The original 11 real-host ACL tests and Rust interop remain required. Ten additional Windows tests run a compiled harness that includes the actual addon and injects races, N-API failures, malformed ACEs and allocation failures. Its filesystem operations use real Windows handles; synthetic descriptors cover owners independently of TokenOwner. These focused tests do not replace real-host qualification. Portable tests establish normalized policy/loader behavior and POSIX filesystem behavior only. Real Windows CI qualifies the tested OS/filesystem/runtime combinations; it is not a claim that mocks prove Windows security or that arbitrary shares are supported.

## Releases

The npm release workflow is [`.github/workflows/release-npm.yml`](https://github.com/cortexkit/subconscious/blob/master/.github/workflows/release-npm.yml). A `private-files@<version>` tag must match `package.json`; it builds Windows x64 and ARM64 prebuilds, merges the artifacts, checks both PE architectures and delayed imports, then uses the existing OIDC trusted-publishing step. Before publishing, configure the package's npm Trusted Publisher for owner `cortexkit`, repository `subconscious`, and workflow filename `release-npm.yml`. Follow the repository's [trusted-publishing setup guide](https://github.com/cortexkit/subconscious/blob/master/docs/npm-trusted-publishing.md) for initial package setup. The qualification workflow never publishes.

Before tagging, require both `private-files-prebuilds` jobs (x64 and arm64) and all three `acl` jobs (`windows-latest`, `windows-2022`, `windows-11-arm`) in [`.github/workflows/private-files.yml`](https://github.com/cortexkit/subconscious/blob/master/.github/workflows/private-files.yml) to pass. They cover Node 24, Bun 1.3.14 and Bun 1.4.2, including the second-user/public-control proofs, Rust interop, negative controls and the 250 ms event-loop-delay bound; the ARM runner also tests emulated x64 Node. Build the pinned Rust fixture from the package folder with `cargo +stable build --locked --manifest-path test/fixtures/rust/Cargo.toml --target-dir test/fixtures/rust/target` before running the Windows harness manually. macOS/Linux tests do not qualify Windows ACL enforcement or native loading.
