# SubcFed exact-byte fixture provenance

Every fixture in this directory is an exact-byte golden vector for the
SubcFed wire layer. The fixtures are generated deterministically from the
Swift implementation under `Sources/SubcFed/` using fixed cryptographic
entropy, so the same source + same FED_HEAD-pinned wire contract always
produces the same bytes.

## FED_HEAD pin

The vendored fed-wire and rdv-wire contracts live at
`.cortexkit/alfonso/evidence/fed-mobile/`. The normative revision is pinned
by `FED_HEAD.txt`:

```
FED_HEAD = 281f070
```

The wire formats, frame type registry, hello fields, catalog schema,
effect-ledger headers, keepalive/bye semantics, and outer-record framing
are defined by the FED_HEAD-pinned `docs/fed-wire.md` (revision r6) and
`docs/rdv-wire.md`. No fixture restates or modifies those contracts; each
fixture is a concrete byte instance of the normative form.

## Generation command

Fixtures are generated by the Swift test helper
`FixtureGenerator.swift` in this directory. The generator is deterministic:
it uses `FedFixedNoiseEntropy` with fixed byte streams so every IK
handshake message, transport record, and fed frame is reproducible.

To regenerate every fixture hex file and verify byte parity:

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift test --package-path clients/subc-client-swift \
  --filter SubcFedTests.FixtureByteParityTests
```

The test suite both generates the in-memory bytes from the frozen source
and compares them against the checked-in `.hex` files in this directory.
A drift in any fixture fails the test, so the checked-in bytes and the
source are held in lockstep.

## Fixture inventory

### Outer records (`outer-records.hex`)

TCP and WebSocket outer records: `u32 LE length || Noise message`. Covers
a handshake-length payload and a transport-length payload. Both carriers
use the identical outer-record format; the only difference is that a
WebSocket binary message carries exactly one complete record while TCP
streams them.

### Noise IK handshake (`noise-ik-handshake.hex`)

Both IK handshake messages under deterministic entropy:
- message 1 (initiator → responder): 96 bytes — 32 ephemeral || 48
  encrypted-static || 16 AEAD tag over empty payload.
- message 2 (responder → initiator): 48 bytes — 32 ephemeral || 16 AEAD
  tag over empty payload.

The initiator static key is `0x11 * 32`, the responder static key is
`0x22 * 32`, the initiator ephemeral entropy is `0x33 * 32`, and the
responder ephemeral entropy is `0x44 * 32`. The prologue is `subc-fed/1`.

### Noise transport records (`noise-transport-records.hex`)

Two Noise transport records (ciphertext + 16-byte AEAD tag) produced by
the established session's send key at nonces 0 and 1. The plaintext for
nonce 0 is the keepalive fed frame; the plaintext for nonce 1 is the bye
fed frame. This ties the transport layer to the frame layer so a single
byte flip in a transport record fails authentication and delivers zero
bytes to the fed-frame parser.

### Fed frame headers and bodies (`fed-frames.hex`)

Every baseline fed-frame wire form required by the normative acceptance
criteria, each encoded as `u32 LE header_len || header || u32 LE body_len
|| body`:

- `hello` — v1 defaults, `mgmt-v1` + `effects-v1`, fixed incarnation and
  ledger epoch, 32-lowercase-hex connection attempt id.
- `bye` — `fed_goodbye` code.
- `keepalive` — bodyless.
- `keepalive` with `confirmed_watermark` — effects-v1 only.
- `catalog` — empty snapshot `{"modules":[]}`, generation 1.
- `call` (management, pure query) — `surface:"management"`,
  `module:"alfonso-core"`, `deadline_ms:300000`, body
  `{"method":"board.state","params":{}}`.
- `call` (mutation) — `mutating:true`, `module:"rooms"`,
  `deadline_ms:300000`, body `{"name":"post","arguments":{}}`.
- `call` with `confirmed_watermark` — effects-v1 only.
- `call_frame` (response) — `k:"response"`, `binary:false`, `last:true`.
- `call_frame` (error) — `k:"error"`, `binary:false`, `last:true`.
- `call_frame` with `body_omitted:true` — empty body.
- `call_cancel` — bodyless.
- `effect_status` — bodyless, effects-v1 only.
- `effect_status_result` (recorded) — `status:"recorded"`,
  `k:"response"`, `ledger_complete:true`, body present.
- `effect_status_result` (not_found) — `status:"not_found"`,
  `ledger_complete:true`, empty body.
- `effect_status_result` (expired) — `status:"expired"`,
  `ledger_complete:true`, empty body.
- `effect_status_result` (body_omitted) — `status:"recorded"`,
  `body_omitted:true`, empty body.

### rdv-wire vectors

The rdv-wire golden vectors ARE copied into `Fixtures/rdv-wire/`, and the
fixture tests read that copy from the source tree at test time. An earlier
version of this note claimed they were read directly from the vendored
evidence directory and therefore picked up contract updates automatically.
That was not true, and the claim was worse than saying nothing: it described
a currency guarantee that nothing enforced.

A copy is a SNAPSHOT. It records what the producer emitted once, so a change
on the producing side breaks nothing here and the divergence surfaces at a
live handshake instead of at a build. `RdvVectorCurrencyTests` turns it into a
PIN by asserting each vector's SHA-256 against a digest written in the test
(not computed from the file, which would let any regenerated copy satisfy it),
plus the vector set itself, since a vector added or removed upstream is also a
contract change.

The same bytes are consumed by the TypeScript rendezvous worker and the Rust
cloud vocabulary, both of which read them from the producing repository's own
`test-vectors/rdv-wire/`. Updating a vector here means the contract moved:
read what changed before touching the digest.

The conformance tests verify canonical key ordering, decimal-string numerics,
NFC enforcement, minimal escaping, duplicate-key rejection, and the depth-128
boundary.
## Historical instance data

The committed fed-frame vectors embed `module:"alfonso-core"` as their call
target. That module was renamed to `prefrontal-core` fleet-wide (2026-08);
the string here is INSTANCE DATA inside byte-pinned goldens, not a contract
claim, and it is deliberately left unrenamed: regenerating every golden to
update a test-arbitrary string would churn the byte-parity artifacts for
zero wire value. A rename sweep will match this directory without there
being anything to change. If the goldens are ever regenerated for a real
contract reason, use `prefrontal-core` in the new bytes.
