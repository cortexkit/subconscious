The CortexKit Landscape

SUBC — the multiplexed splice-router

A per-user local daemon that supervises CortexKit's modules and routes their traffic — forwarding packets by reading only a fixed 17-byte header, never deserializing the body.

Why it exists. AFT (the tool engine) ran as an OpenCode/Pi-managed binary behind a single NDJSON lane — every tool call queued behind the previous one (head-of-line blocking). SUBC moves AFT to a daemon-supervised module, makes it MCP-capable, and removes the single-lane constraint so non-mutating tools run concurrently.

The thin-core bet

SUBC reads only the envelope header to make a routing decision; payloads are opaque bytes it forwards without parsing. That keeps it fast, schema-decoupled, and means a new module needs zero edits to subc-core — a module is just a process that speaks the wire and declares a manifest. Channel 0 is the control plane (RPCs); non-zero channels are data-plane routes the router rewrites between independent client-side and module-side channel spaces.

The 17-byte envelope

Every frame is prefixed with a fixed 17-byte header. The router makes its entire decision from this header — the first 5 bytes are a frozen prefix that never changes across protocol versions.

Frame types

The type byte selects one of twelve frame kinds — locked and AFT-co-signed.

Zero-deserialization routing. The router reads channel to pick the connection and type to track flow-control credit — then forwards the opaque body untouched, rewriting only the channel field between client and module channel spaces. It never parses a tool's arguments or results.
