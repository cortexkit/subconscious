# Supervisor health v1 examples

Each `.jsonl` file has two lines: a client control request body followed by its
reply body. The bytes on each line are the compact JSON bodies used on the
control channel; the newline separates records and is not part of either body.
Module names, timestamps and readings are invented. The examples are serialized
by the daemon's response frame encoder from fixed test data using subc-daemon
0.50.0; they are not captures of a running installation.

- `health-ok-degraded` and `list-ok-degraded` show healthy and degraded modules.
  The degraded health reply includes a human-readable detail and metrics.
- `health-failing-unknown` and `list-failing-unknown` show a failing module and
  one whose health has never been reported.
- `health-disabled` and `list-disabled` show an unprobed, disabled module. Its
  unknown health is not evidence that it is healthy or failing.

The list replies show health alongside lifecycle information. Cached health
replies can contain detail and metrics not present in the list. Ignore unknown
fields when reading either reply so newer daemons can add information.

Regenerate the files on Linux with
`UPDATE_SUPERVISOR_HEALTH_VECTORS=1 scripts/test-daemon-lib.sh -- --exact control::tests::supervisor_health_v1_vectors`,
then update `SHA256SUMS` after reviewing any changes. Run the same command without
the environment variable to compare the generated bytes with these files.
